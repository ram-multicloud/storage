# Azure File Share — Complete Guide

## What is Azure File Share?

**Azure Files** (or Azure File Share) is a fully managed cloud file storage service that lets you create network file shares accessible via the standard **SMB (Server Message Block)** and **NFS (Network File System)** protocols. You can mount an Azure file share concurrently on cloud VMs, on-premises servers, or even your own PC — just like a regular network drive.

**Key characteristics:**
- Lives inside an **Azure Storage Account**
- Accessed via SMB (Windows/Linux/macOS) or NFS (Linux only)
- Can be mounted from multiple machines simultaneously
- Supports snapshots, soft delete, and backup integration
- Can be used to replace on-prem file servers, share app configs, host "lift-and-shift" workloads, or serve as a persistent volume for containers (e.g., AKS)
- Public URL format: `https://<storageaccountname>.file.core.windows.net/<sharename>`

## Types / Tiers of Azure File Share

Azure Files offers two main storage tiers, and Standard itself has three access sub-tiers:

| Tier | Backing Storage | Protocols | Billing Model | Best For |
|---|---|---|---|---|
| **Premium** | SSD | SMB, NFS | Pay for provisioned capacity | Latency-sensitive workloads (databases, dev environments, CI/CD build caches) |
| **Standard – Transaction Optimized** | HDD | SMB, REST | Pay per usage | High-transaction workloads like backups/migrations |
| **Standard – Hot** | HDD | SMB, REST | Pay per usage | General-purpose shares with moderate, regular access |
| **Standard – Cool** | HDD | SMB, REST | Pay per usage | Infrequently accessed / archival-style data |

### Premium
- SSD-backed, created inside a **FileStorage** storage account kind (premium file shares can't share an account with other storage types)
- Offers single-digit-millisecond latency and much higher IOPS/throughput than Standard
- Supports both SMB and NFS protocols
- Redundancy options: LRS, ZRS

### Standard (Transaction Optimized / Hot / Cool)
- HDD-backed, created inside a **General Purpose v2 (GPv2)** storage account
- All three access tiers run on the same underlying hardware, so their performance (IOPS/throughput) is broadly comparable — the real difference between them is cost structure (storage cost vs. transaction cost)
- Redundancy options: LRS, ZRS, GRS, GZRS
- You can change the access tier (Transaction Optimized / Hot / Cool) at any time without recreating the share

### Redundancy options (apply to both tiers, availability varies)
- **LRS** — Locally Redundant Storage (3 copies, single datacenter)
- **ZRS** — Zone Redundant Storage (copies across availability zones)
- **GRS** — Geo-Redundant Storage (copies in a secondary region)
- **GZRS** — Geo-Zone-Redundant Storage (zone + geo redundancy)

## Prerequisites for the CLI Examples

Install and sign in with the Azure CLI:

```bash
# Install (Linux example, Debian/Ubuntu)
curl -sL https://aka.ms/InstallAzureCLIDeb | sudo bash

# macOS
brew install azure-cli

# Windows (via winget)
winget install -e --id Microsoft.AzureCLI
```

Then log in:
```bash
az login
```

## Example 1: Create a Standard File Share (Hot tier)

```bash
# 1. Create a resource group
az group create \
  --name myResourceGroup \
  --location eastus

# 2. Create a General Purpose v2 storage account
az storage account create \
  --name mystorageacct1234 \
  --resource-group myResourceGroup \
  --location eastus \
  --sku Standard_LRS \
  --kind StorageV2

# 3. Get the storage account key (needed to create/manage the share)
az storage account keys list \
  --resource-group myResourceGroup \
  --account-name mystorageacct1234 \
  --query "[0].value" -o tsv

# 4. Create the file share (Standard, Hot access tier, 100 GiB quota)
az storage share-rm create \
  --resource-group myResourceGroup \
  --storage-account mystorageacct1234 \
  --name myfileshare \
  --quota 100 \
  --access-tier Hot
```

## Example 2: Create a Premium File Share

Premium shares require a **FileStorage** account kind and Premium SKU.

```bash
# 1. Create a premium (FileStorage) storage account
az storage account create \
  --name mypremiumfiles1234 \
  --resource-group myResourceGroup \
  --location eastus \
  --sku Premium_LRS \
  --kind FileStorage

# 2. Create the premium file share (provisioned capacity, e.g. 200 GiB)
az storage share-rm create \
  --resource-group myResourceGroup \
  --storage-account mypremiumfiles1234 \
  --name mypremiumshare \
  --quota 200
```

## Example 3: Mounting the File Share

### On Linux (SMB)
```bash
sudo mkdir -p /mnt/myfileshare

sudo mount -t cifs //mystorageacct1234.file.core.windows.net/myfileshare /mnt/myfileshare \
  -o vers=3.0,username=mystorageacct1234,password=<storage-account-key>,dir_mode=0777,file_mode=0777,serverino
```

### On Linux (NFS — Premium tier only)
```bash
sudo mkdir -p /mnt/myfileshare

sudo mount -t nfs mystorageacct1234.file.core.windows.net:/mystorageacct1234/myfileshare /mnt/myfileshare \
  -o vers=4,minorversion=1,sec=sys
```

### On Windows (PowerShell)
```powershell
$connectTestResult = Test-NetConnection -ComputerName mystorageacct1234.file.core.windows.net -Port 445

if ($connectTestResult.TcpTestSucceeded) {
    net use Z: \\mystorageacct1234.file.core.windows.net\myfileshare /u:AZURE\mystorageacct1234 <storage-account-key>
} else {
    Write-Error -Message "Unable to reach the Azure storage account via port 445."
}
```

## Example 4: Common File Share Operations via CLI

```bash
# Upload a file to the share
az storage file upload \
  --account-name mystorageacct1234 \
  --account-key <storage-account-key> \
  --share-name myfileshare \
  --source ./localfile.txt \
  --path localfile.txt

# List files/directories in the share
az storage file list \
  --account-name mystorageacct1234 \
  --account-key <storage-account-key> \
  --share-name myfileshare \
  --output table

# Download a file from the share
az storage file download \
  --account-name mystorageacct1234 \
  --account-key <storage-account-key> \
  --share-name myfileshare \
  --path localfile.txt \
  --dest ./downloaded.txt

# Create a directory in the share
az storage directory create \
  --account-name mystorageacct1234 \
  --account-key <storage-account-key> \
  --share-name myfileshare \
  --name logs

# Take a snapshot of the share
az storage share snapshot \
  --account-name mystorageacct1234 \
  --account-key <storage-account-key> \
  --name myfileshare

# Delete a file share
az storage share-rm delete \
  --resource-group myResourceGroup \
  --storage-account mystorageacct1234 \
  --name myfileshare \
  --yes
```

## Example 5: Using Azure File Share as a Kubernetes (AKS) Persistent Volume

A common real-world use case — mounting Azure Files as shared, ReadWriteMany storage for pods.

```bash
# Create a Kubernetes secret with the storage account credentials
kubectl create secret generic azure-secret \
  --from-literal=azurestorageaccountname=mystorageacct1234 \
  --from-literal=azurestorageaccountkey=<storage-account-key>
```

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: azurefile-pv
spec:
  capacity:
    storage: 100Gi
  accessModes:
    - ReadWriteMany
  azureFile:
    secretName: azure-secret
    shareName: myfileshare
    readOnly: false
```

## Quick Comparison: When to Use What

| Scenario | Recommended Tier |
|---|---|
| Lift-and-shift a Windows file server | Standard – Hot |
| Backup / migration staging area | Standard – Transaction Optimized |
| Archive / rarely accessed logs | Standard – Cool |
| Databases or dev/CI build caches needing low latency | Premium |
| Shared storage for containers (AKS, ACI) | Premium (NFS) or Standard (SMB) |

## Best Practices

1. Store storage account keys in **Azure Key Vault** rather than hardcoding them in scripts.
2. Use **private endpoints** to keep file share traffic off the public internet.
3. Enable **soft delete** on the storage account to protect against accidental deletion.
4. For production workloads needing low latency, prefer **Premium** — Standard tiers are HDD-backed and share the same performance ceiling regardless of access tier chosen.
5. Use `az storage share-rm update --access-tier` to change a Standard share's tier without downtime, based on actual access patterns.
6. Right-size the share **quota** — for Standard you're billed per GiB used; for Premium you're billed per GiB **provisioned**, so oversizing costs more immediately.
