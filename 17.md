# File Share — Concepts, AWS EFS, and Azure Files (AFS)

## 1. What Is a File Share (Generic Concept)

A **file share** is centralized storage exposed over a network so that multiple clients (VMs, servers, laptops) can read/write the same files simultaneously — instead of each machine having its own isolated local disk.

Two common protocols:

| Protocol | Typical OS | Description |
|----------|-----------|-------------|
| **NFS** (Network File System) | Linux/Unix | Mounts a remote directory as if it were local |
| **SMB/CIFS** (Server Message Block) | Windows (also supported on Linux/macOS) | Mounts a remote share as a network drive |

### Generic Example (on-prem)

Imagine a Linux NFS server exporting `/data/shared`:

```bash
# On the NFS server
echo "/data/shared 10.0.0.0/24(rw,sync,no_subtree_check)" >> /etc/exports
exportfs -a
systemctl restart nfs-kernel-server
```

```bash
# On a Linux client
sudo mount -t nfs 10.0.0.5:/data/shared /mnt/shared
```

Now any file written to `/mnt/shared` by one client instantly appears for every other client mounting the same export — that's the core idea. Cloud providers offer this as a **managed service** so you don't have to run/patch/scale the NFS or SMB server yourself.

- **AWS EFS** = managed NFS file share
- **Azure Files (AFS)** = managed SMB (and NFS) file share

## 2. AWS EFS (Elastic File System)

### How It Works

- EFS is a fully managed **NFS (v4.1)** file system.
- It's **regional**: you create one EFS filesystem, then create **mount targets** in each Availability Zone (subnet) where you want clients to connect.
- Storage auto-scales (no pre-provisioned size) and is billed per GB actually used.
- Multiple EC2 instances (and Lambda, ECS, EKS) can mount the same EFS filesystem concurrently.
- Access is controlled via **Security Groups** (on the mount target's ENI) and optionally **IAM policies** + **access points**.

### Create an EFS Filesystem (AWS CLI)

```bash
aws efs create-file-system \
  --creation-token my-efs-token \
  --performance-mode generalPurpose \
  --throughput-mode bursting \
  --encrypted
```

Note the returned `FileSystemId` (e.g. `fs-0123456789abcdef0`).

### Create a Mount Target (per subnet/AZ)

```bash
aws efs create-mount-target \
  --file-system-id fs-0123456789abcdef0 \
  --subnet-id subnet-0abc1234 \
  --security-groups sg-0efs12345
```

The security group must allow inbound **NFS (port 2049)** from the EC2 instances that will mount it.

### Mount on Linux (EC2)

```bash
# Install the NFS/EFS client
sudo yum install -y amazon-efs-utils      # Amazon Linux
# or
sudo apt-get install -y nfs-common        # Ubuntu

# Create a mount point
sudo mkdir -p /mnt/efs

# Mount using the EFS helper (recommended — supports EFS mount points + encryption in transit)
sudo mount -t efs -o tls fs-0123456789abcdef0:/ /mnt/efs

# Or via plain NFS
sudo mount -t nfs4 -o nfsvers=4.1 fs-0123456789abcdef0.efs.us-east-1.amazonaws.com:/ /mnt/efs
```

Persist across reboots via `/etc/fstab`:

```
fs-0123456789abcdef0:/ /mnt/efs efs _netdev,tls 0 0
```

### Mount on Windows

**EFS does not natively support SMB/Windows mounting** — EFS is NFS-only. To use EFS from Windows, you'd typically:
- Mount it on a Linux instance and re-share it via Samba, or
- Use **AWS Storage Gateway (File Gateway)** to expose EFS as an SMB share to Windows clients.

For native Windows file shares on AWS, use **Amazon FSx for Windows File Server** instead (SMB-native), or Azure Files if operating in Azure.

## 3. Azure Files (AFS)

### How It Works

- Azure Files is a fully managed file share supporting **SMB (3.0/3.1.1)** and **NFS (4.1)** protocols.
- Lives inside an **Azure Storage Account** as a "File Share" resource.
- Can be mounted directly from on-prem or cloud VMs (Windows, Linux, macOS) over SMB, or mounted via **Azure File Sync** to cache it on-prem.
- Two tiers: **Standard** (HDD-backed) and **Premium** (SSD-backed, provisioned IOPS).
- NFS shares require Premium tier + require the storage account to be in a VNet (no public endpoint).

### Create a Storage Account + File Share (Azure CLI)

```bash
# Create resource group (if needed)
az group create --name myRG --location eastus

# Create storage account
az storage account create \
  --name mystorageacct123 \
  --resource-group myRG \
  --location eastus \
  --sku Standard_LRS \
  --kind StorageV2

# Create the file share (SMB)
az storage share-rm create \
  --resource-group myRG \
  --storage-account mystorageacct123 \
  --name myfileshare \
  --quota 100
```

Get the storage account key (needed for SMB mount auth):

```bash
az storage account keys list \
  --resource-group myRG \
  --account-name mystorageacct123 \
  --query "[0].value" -o tsv
```

### Mount on Windows

```powershell
$connectTestResult = Test-NetConnection -ComputerName mystorageacct123.file.core.windows.net -Port 445

if ($connectTestResult.TcpTestSucceeded) {
    # Save the storage account key as a persistent credential
    cmd.exe /C "cmdkey /add:`"mystorageacct123.file.core.windows.net`" /user:`"localhost\mystorageacct123`" /pass:`"<storage-account-key>`""

    # Mount as drive Z:
    New-PSDrive -Name Z -PSProvider FileSystem -Root "\\mystorageacct123.file.core.windows.net\myfileshare" -Persist
} else {
    Write-Error "Port 445 (SMB) blocked — mount will fail. Check firewall/ISP."
}
```

Or the simple one-liner (if port 445 is already confirmed open):

```powershell
net use Z: \\mystorageacct123.file.core.windows.net\myfileshare /u:localhost\mystorageacct123 <storage-account-key>
```

### Mount on Linux (SMB)

```bash
sudo apt-get install -y cifs-utils     # Debian/Ubuntu
# or
sudo yum install -y cifs-utils         # RHEL/CentOS

sudo mkdir -p /mnt/azurefiles

sudo mount -t cifs \
  //mystorageacct123.file.core.windows.net/myfileshare \
  /mnt/azurefiles \
  -o username=mystorageacct123,password=<storage-account-key>,serverino,nosharesock,actimeo=30,mfsymlinks
```

Persist across reboots via `/etc/fstab`:

```
//mystorageacct123.file.core.windows.net/myfileshare /mnt/azurefiles cifs username=mystorageacct123,password=<storage-account-key>,serverino,nosharesock,actimeo=30,mfsymlinks,_netdev 0 0
```

### Mount on Linux (NFS — Premium tier only)

```bash
sudo mkdir -p /mnt/azurefiles-nfs
sudo mount -t nfs mystorageacct123.file.core.windows.net:/mystorageacct123/myfileshare /mnt/azurefiles-nfs -o vers=4,minorversion=1,sec=sys
```

(Requires the storage account to be in the same VNet, or peered/private-endpoint connected — NFS shares have no public endpoint.)

## 4. Quick Comparison — EFS vs Azure Files

| Feature | AWS EFS | Azure Files (AFS) |
|---|---|---|
| Native protocol | NFS only | SMB (default) + NFS (Premium) |
| Windows-native mount | No (needs Storage Gateway) | Yes (native SMB) |
| Linux-native mount | Yes | Yes (SMB or NFS) |
| Scaling | Auto, pay-per-use | Provisioned (Premium) or pay-per-use (Standard) |
| Regional scope | Regional, multi-AZ mount targets | Regional (storage account) |
| Encryption in transit | TLS (via efs-utils) | SMB 3.0 encryption / HTTPS |
| Best fit | Linux workloads, containers, EKS/ECS | Mixed Windows + Linux environments, lift-and-shift file servers |
