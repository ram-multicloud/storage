# S3 File System

S3 itself is **not a file system** — it's object storage (flat key-value store accessed over HTTP/API), not a POSIX filesystem with directories, permissions, or file locking. But it can be made to *behave* like one using extra tooling.

## Ways to Use S3 "as a File System"

### 1. s3fs-fuse
Mounts an S3 bucket as a local directory using FUSE (Filesystem in Userspace).

```bash
sudo apt install s3fs
echo ACCESS_KEY:SECRET_KEY > ~/.passwd-s3fs
chmod 600 ~/.passwd-s3fs

mkdir ~/s3-mount
s3fs mybucket ~/s3-mount -o passwd_file=~/.passwd-s3fs
```

Now `~/s3-mount` behaves like a regular folder — `ls`, `cp`, `cat`, etc. work, but performance is much slower than a real disk (every operation is an API call).

### 2. AWS Storage Gateway (File Gateway)
An AWS-managed appliance (VM or hardware) that presents S3 as an **NFS or SMB share** — used for enterprise on-prem backup/archival workflows without changing existing file-based applications.

### 3. Amazon EFS / FSx (not S3, but often confused)
If you need a *true* POSIX filesystem in AWS (concurrent writes, file locking, low latency), use **EFS** (NFS) or **FSx** instead of trying to force S3 into that role. S3 is best for object storage, not transactional file operations.

## Create an EC2 VM and Mount S3 (AWS CLI)

### 1. Create a key pair (for SSH access)
```bash
aws ec2 create-key-pair --key-name my-key --query 'KeyMaterial' --output text > my-key.pem
chmod 400 my-key.pem
```

### 2. Create a security group (allow SSH)
```bash
aws ec2 create-security-group --group-name my-sg --description "Allow SSH"
aws ec2 authorize-security-group-ingress --group-name my-sg --protocol tcp --port 22 --cidr 0.0.0.0/0
```

### 3. Launch the EC2 instance
```bash
aws ec2 run-instances \
  --image-id ami-0abcdef1234567890 \
  --instance-type t2.micro \
  --key-name my-key \
  --security-groups my-sg \
  --count 1
```
(Replace `ami-0abcdef1234567890` with a current Amazon Linux/Ubuntu AMI ID for your region.)

### 4. Get the public IP
```bash
aws ec2 describe-instances --filters "Name=key-name,Values=my-key" \
  --query "Reservations[].Instances[].PublicIpAddress" --output text
```

### 5. SSH into the instance
```bash
ssh -i my-key.pem ec2-user@<PUBLIC_IP>
```

### 6. Install s3fs and mount the bucket (run inside the VM)
```bash
sudo yum install -y s3fs-fuse   # Amazon Linux
# or: sudo apt install -y s3fs  # Ubuntu

echo ACCESS_KEY:SECRET_KEY > ~/.passwd-s3fs
chmod 600 ~/.passwd-s3fs

mkdir ~/s3-mount
s3fs mybucket ~/s3-mount -o passwd_file=~/.passwd-s3fs
```

### 7. Verify the mount
```bash
df -h | grep s3fs
ls ~/s3-mount
```

### 8. (Optional) Auto-mount on boot
Add to `/etc/fstab`:
```
s3fs#mybucket /home/ec2-user/s3-mount fuse _netdev,passwd_file=/home/ec2-user/.passwd-s3fs 0 0
```

## Example Use Case
A media company keeps its legacy on-prem video-editing software (expects a normal file share) but wants cheap, durable cloud storage. They deploy **Storage Gateway File Gateway**, mount it as an SMB share on editors' machines — files get written locally, and the gateway syncs them to an S3 bucket in the background.

## Key Limitations to Remember
- No native file locking or partial-file edits (must re-upload entire object)
- Eventual consistency historically was a concern (now strongly consistent since Dec 2020)
- Not suitable for databases or apps needing random read/write access
- Latency is much higher than block/file storage
