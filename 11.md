# Amazon EBS (Elastic Block Store)

> **Analogy:** Think of an EC2 instance as a laptop and an EBS volume as an external hard drive you plug into it. The laptop can run without it, but the moment you need persistent storage — or want to move the drive to another laptop — that's what EBS is for.

Amazon EBS is a **block storage service** provided by AWS that is used with EC2 instances. It acts like a **virtual hard disk** attached to a server — data written to it persists independently of the EC2 instance's lifecycle (unlike instance store volumes, which are wiped when the instance stops).

### Key Features

| Feature | What it means |
|---|---|
| Block-level storage | Data is stored in fixed-size blocks, like a traditional disk — not objects (S3) or files (EFS) |
| One instance at a time | An EBS volume can only be attached to a single EC2 instance at once (except Multi-Attach io1/io2) |
| Low latency, high performance | Suited for workloads needing fast, consistent disk I/O |
| Snapshots | Point-in-time backups stored in S3, used for recovery or cloning volumes |
| Manual scaling | You must explicitly resize/modify the volume — it doesn't grow automatically |


1. Create an EBS volume in AWS

3. Format and mount it like a disk
4. Use it for storing data

### Use Cases

- Operating system (boot volumes)
- Databases (MySQL, PostgreSQL, Oracle)
- Transaction-heavy applications
- File systems requiring fast access

### Types of EBS Volumes

| Type | Category | Best for |
|---|---|---|
| **gp3 / gp2** | General purpose SSD | Everyday workloads — web servers, dev/test, small-to-medium databases |
| **io1 / io2** | Provisioned IOPS SSD | High-performance, latency-sensitive workloads — large production databases |
| **st1** | Throughput-optimized HDD | Big sequential-access workloads — big data, log processing |
| **sc1** | Cold HDD | Infrequently accessed data — lowest cost, archival-style storage |

> **Choosing between them:** if the workload is IOPS-hungry (lots of small, random reads/writes — e.g. a busy database), go with io1/io2. If it's throughput-hungry (large sequential reads — e.g. log or big-data processing), st1 is more cost-effective. gp3 is the sensible default for most general workloads.

### Security

- Encryption at rest using AWS KMS
- IAM-based access control
- Snapshot backups for recovery

## EBS Volume Mount Commands

A newly attached EBS volume is raw block storage — it has no partition table and no filesystem yet. These steps take it from "attached but unusable" to "mounted and ready for data."

### Step 1 — Check Attached Disks

```bash
lsblk
```
Lists block devices so you can identify the newly attached volume (e.g. `/dev/nvme1n1`).

### Step 2 — Partition the Volume (using `parted`)

```bash
sudo parted /dev/nvme1n1
```

Inside the parted prompt:

```
(parted) mklabel gpt
(parted) mkpart primary ext4 0% 100%
(parted) quit
```

| Command | What it does |
|---|---|
| `mklabel gpt` | Creates a GPT partition table (recommended for disks > 2TB and modern systems) |
| `mkpart primary ext4 0% 100%` | Creates a single partition spanning the full disk |
| `quit` | Exits parted |

### Step 3 — Format the Partition

```bash
sudo mkfs -t ext4 /dev/nvme1n1p1
```
Writes an ext4 filesystem onto the new partition.

### Step 4 — Create Mount Point & Mount

```bash
sudo mkdir /data
sudo mount /dev/nvme1n1p1 /data
```
Creates the directory `/data` and mounts the partition there.

### Step 5 — Persist Mount (`fstab`)

Without this step, the mount is lost on reboot.

```bash
sudo su -
```

Add the following line to `/etc/fstab`:

```
/dev/nvme1n1p1   /data   ext4   defaults,nofail   0   2
```

> `nofail` prevents the instance from failing to boot if this volume is ever missing at boot time — a good safety default for secondary data volumes.

Then test:

```bash
sudo mount -a
```

### Step 6 — Verify

```bash
df -h
lsblk
mount
```

### Step 7 — Set Ownership

```bash
sudo chown ec2-user:ec2-user /data
```
Grants the `ec2-user` account ownership so applications running as that user can read/write to `/data`.
