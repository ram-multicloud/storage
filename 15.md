# Azure Disk Storage — Managed Disks

## 1. What a managed disk is

An Azure **managed disk** is block storage attached to a virtual machine and presented to the OS as a local drive (`/dev/sdc` on Linux, a drive letter on Windows). Azure manages the underlying storage account, replication and placement — you only declare size, type and redundancy.

## 2. Disk roles on a VM

| Role | Description | Persistent? |
|---|---|---|
| **OS disk** | Holds the operating system. Created automatically with the VM. Max 4 TiB. Labelled `/dev/sda` (Linux) or `C:` (Windows). | Yes |
| **Data disk** | Extra disks you attach for application data, databases, logs. Up to 64 TiB each; count limited by VM size. | Yes |
| **Temporary disk** | Local SSD on the physical host. Shows as `/dev/sdb` or `D:`. Use only for page/swap files and scratch. | **No — wiped on deallocate/host maintenance** |

> Never store application data on the temporary disk. It is lost whenever the VM moves hosts.

## 3. Disk types

Azure offers five managed disk types.

| Type | SKU string | Max IOPS | Max throughput | Latency | OS disk? | Typical use |
|---|---|---|---|---|---|---|
| **Ultra Disk** | `UltraSSD_LRS` | ~400,000 | ~10,000 MB/s | sub-ms | No (data disk only) | SAP HANA, top-tier SQL/Oracle, transaction-heavy workloads |
| **Premium SSD v2** | `PremiumV2_LRS` | ~80,000 | ~1,200 MB/s | sub-ms | No (data disk only) | Most new production workloads — best price/performance |
| **Premium SSD** | `Premium_LRS` | ~20,000 | ~900 MB/s | low ms | Yes | Production VMs, general business apps |
| **Standard SSD** | `StandardSSD_LRS` | ~6,000 | ~750 MB/s | ms | Yes | Web servers, dev/test, light enterprise apps |
| **Standard HDD** | `Standard_LRS` | ~2,000 | ~500 MB/s | variable | Yes | Backup, archive, infrequently accessed data |

Figures are ceilings for the largest disk in each family; actual IOPS depend on disk size and on the VM SKU's own disk throughput cap.

### Notes on each type

**Ultra Disk**
- Capacity 4 GiB – 64 TiB in 1 GiB increments.
- Capacity, IOPS and throughput are set **independently** — you pay for each.
- Must be enabled per-VM at creation (`--ultra-ssd-enabled true`) and is limited to specific VM SKUs and availability zones.
- Default quota is 100 TiB per region per subscription.

**Premium SSD v2**
- No fixed size tiers. Any supported size, and IOPS/throughput tuned separately **without downtime**.
- Generally cheaper than Premium SSD at higher performance. Recommended default for new production deployments.
- Cannot be used as an OS disk; data disk only. Requires a zonal VM.

**Premium SSD**
- Fixed size tiers P1 … P80. Capacity and performance are bundled — to get more IOPS you buy a bigger disk.
- Supports **host caching** (ReadOnly / ReadWrite / None) and bursting.
- The long-standing production baseline; supported as an OS disk everywhere.

**Standard SSD**
- Consistent latency at low cost, but no guaranteed IOPS (best-effort).
- Billed on capacity plus transactions.

**Standard HDD**
- Cheapest per GB. Spinning media, variable latency.
- Microsoft has announced retirement of the Standard HDD option for new VDI/OS-disk scenarios — check the current Azure product lifecycle page before designing around it.

### Choosing quickly

```
Mission-critical DB, sub-ms, extreme IOPS   -> Ultra Disk
New production workload, needs tuning       -> Premium SSD v2
Production OS disk / classic production VM  -> Premium SSD
Dev, test, web servers                      -> Standard SSD
Backup, archive, rarely read                -> Standard HDD
```

## 4. Redundancy options

| Suffix | Meaning | Notes |
|---|---|---|
| `_LRS` | Locally redundant — 3 copies in one datacentre | Default, cheapest |
| `_ZRS` | Zone redundant — copies across 3 availability zones | Available for Premium SSD and Standard SSD in supported regions; allows disk to survive a zone failure and be attached to a VM in another zone |

Example SKUs: `Premium_LRS`, `Premium_ZRS`, `StandardSSD_ZRS`.

## 5. Host caching

Applies to Premium SSD and Standard disks. Set per data disk.

| Setting | Use for |
|---|---|
| `ReadOnly` | Read-heavy data disks, database data files |
| `ReadWrite` | OS disks (default) |
| `None` | Write-heavy disks, database log files, any disk where writes must not be cached |

## 6. Steps — create and attach a data disk (Azure CLI)

### Step 1: Log in and set variables

```bash
az login
az account set --subscription "<subscription-id>"

RG=devops-rg
LOC=centralindia
VM=devops-vm
DISK=devops-data-disk
```

### Step 2: Create a resource group (if needed)

```bash
az group create --name $RG --location $LOC
```

### Step 3: Create the managed disk

```bash
az disk create \
  --resource-group $RG \
  --name $DISK \
  --location $LOC \
  --sku Premium_LRS \
  --size-gb 128
```

For Premium SSD v2, performance is set explicitly:

```bash
az disk create \
  --resource-group $RG \
  --name $DISK \
  --location $LOC \
  --sku PremiumV2_LRS \
  --size-gb 128 \
  --disk-iops-read-write 5000 \
  --disk-mbps-read-write 200 \
  --zone 1
```

### Step 4: Attach the disk to the VM

```bash
az vm disk attach \
  --resource-group $RG \
  --vm-name $VM \
  --name $DISK \
  --caching ReadOnly
```

To create and attach in one command:

```bash
az vm disk attach \
  --resource-group $RG \
  --vm-name $VM \
  --name $DISK \
  --new \
  --size-gb 128 \
  --sku StandardSSD_LRS
```

### Step 5: Verify the attachment

```bash
az vm show --resource-group $RG --name $VM \
  --query "storageProfile.dataDisks[].{name:name, lun:lun, sizeGb:diskSizeGb, sku:managedDisk.storageAccountType}" \
  --output table
```

## 7. Steps — initialise the disk inside a Linux VM

### Step 1: Find the new device

```bash
lsblk
# or
sudo fdisk -l
```

The new disk usually appears as `/dev/sdc` (with `/dev/sda` = OS, `/dev/sdb` = temporary). Confirm by size, not by letter.

### Step 2: Partition (optional — you may format the whole device)

```bash
sudo parted /dev/sdc --script mklabel gpt mkpart primary xfs 0% 100%
sudo partprobe /dev/sdc
```

### Step 3: Create a filesystem

```bash
sudo mkfs.xfs /dev/sdc1
# or
sudo mkfs.ext4 /dev/sdc1
```

### Step 4: Mount it

```bash
sudo mkdir -p /data
sudo mount /dev/sdc1 /data
df -h /data
```

### Step 5: Make the mount persistent using UUID

Device letters can change across reboots, so always mount by UUID.

```bash
sudo blkid /dev/sdc1
# copy the UUID value

echo 'UUID=<uuid-here>  /data  xfs  defaults,nofail  0  2' | sudo tee -a /etc/fstab

sudo mount -a          # test before rebooting
```

`nofail` prevents the VM from failing to boot if the disk is missing.

### Step 6: Set ownership

```bash
sudo chown -R $USER:$USER /data
```

## 8. Steps — initialise the disk inside a Windows VM

1. Open **Disk Management** (`diskmgmt.msc`).
2. The new disk appears as *Offline / Unallocated* — right-click, choose **Online**, then **Initialize Disk** (GPT).
3. Right-click the unallocated space → **New Simple Volume**.
4. Assign a drive letter, format as NTFS, set an allocation unit size (64K is common for SQL data volumes), give it a label.

PowerShell equivalent:

```powershell
Get-Disk | Where-Object PartitionStyle -eq 'RAW' |
  Initialize-Disk -PartitionStyle GPT -PassThru |
  New-Partition -AssignDriveLetter -UseMaximumSize |
  Format-Volume -FileSystem NTFS -NewFileSystemLabel "Data" -Confirm:$false
```

---

## 9. Steps — via the Azure Portal

1. **Portal → Virtual machines → select the VM → Settings → Disks**.
2. Under *Data disks*, click **Create and attach a new disk**.
3. Enter a disk name, choose **Storage type** (Premium SSD, Standard SSD, etc.), **Size**, and **Host caching**.
4. Click **Apply**.
5. Connect to the VM and initialise/format the disk as in section 7 or 8.

## 10. Common day-2 operations

### Resize a disk

Disks can only grow, never shrink. Premium SSD v2 and Ultra Disk resize online; other types require the VM to be deallocated.

```bash
az vm deallocate --resource-group $RG --name $VM
az disk update --resource-group $RG --name $DISK --size-gb 256
az vm start --resource-group $RG --name $VM
```

Then grow the filesystem inside the VM:

```bash
sudo growpart /dev/sdc 1
sudo xfs_growfs /data          # xfs
sudo resize2fs /dev/sdc1       # ext4
```

### Change the disk type

```bash
az vm deallocate --resource-group $RG --name $VM
az disk update --resource-group $RG --name $DISK --sku StandardSSD_LRS
az vm start --resource-group $RG --name $VM
```

### Snapshot a disk

```bash
DISK_ID=$(az disk show -g $RG -n $DISK --query id -o tsv)

az snapshot create \
  --resource-group $RG \
  --name ${DISK}-snap-$(date +%Y%m%d) \
  --source $DISK_ID
```

### Create a new disk from a snapshot

```bash
SNAP_ID=$(az snapshot show -g $RG -n ${DISK}-snap-20260916 --query id -o tsv)

az disk create \
  --resource-group $RG \
  --name ${DISK}-restored \
  --source $SNAP_ID \
  --sku Premium_LRS
```

### Detach a disk

```bash
az vm disk detach --resource-group $RG --vm-name $VM --name $DISK
```

Unmount inside the OS **before** detaching, and remove the `/etc/fstab` line.

### Delete a disk

```bash
az disk delete --resource-group $RG --name $DISK --yes
```

## 11. Terraform example

```hcl
resource "azurerm_managed_disk" "data" {
  name                 = "devops-data-disk"
  location             = azurerm_resource_group.rg.location
  resource_group_name  = azurerm_resource_group.rg.name
  storage_account_type = "Premium_LRS"
  create_option        = "Empty"
  disk_size_gb         = 128
}

resource "azurerm_virtual_machine_data_disk_attachment" "data" {
  managed_disk_id    = azurerm_managed_disk.data.id
  virtual_machine_id = azurerm_linux_virtual_machine.vm.id
  lun                = 0
  caching            = "ReadOnly"
}
```

## 12. Gotchas

| Issue | Cause / fix |
|---|---|
| Data gone after reboot | Wrote to the temporary disk (`/dev/sdb`, `D:`) |
| VM won't boot after adding a disk | `/etc/fstab` entry without `nofail`, or wrong UUID |
| Disk mounts on wrong device after reboot | Mounted by `/dev/sdX` instead of UUID |
| Disk IOPS lower than the disk tier promises | VM SKU disk throughput cap is the bottleneck, not the disk |
| Cannot attach Premium SSD v2 / Ultra | VM SKU, region or zone does not support it; Ultra needs `--ultra-ssd-enabled` at VM creation |
| Cannot shrink a disk | Not supported — create a smaller disk and copy the data |
| Disk still billed after VM delete | Data disks default to *detach* on VM delete; delete them explicitly |
