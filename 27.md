# Azure Data Services: Managed Redis, Cosmos DB, Table Storage, AI Search, Data Explorer

A practical guide to five Azure data services: what each one is, when to use it, how to create it, and how to insert and read data.

## Quick Comparison

| Service | Type | Best For | Query Style |
|---|---|---|---|
| Azure Managed Redis | In-memory key-value / data structure store | Caching, sessions, leaderboards, rate limiting, vector cache | Redis commands |
| Azure Cosmos DB | Globally distributed multi-model NoSQL | Low-latency apps, catalogs, profiles, IoT, global apps | SQL-like (NoSQL API), MongoDB, Cassandra, Gremlin, Table |
| Azure Table Storage | Simple NoSQL key-attribute store | Cheap, massive, schemaless structured data | OData filters (PartitionKey / RowKey) |
| Azure AI Search | Search engine (full-text, vector, hybrid) | Website/app search, RAG for LLMs | Search syntax, OData filters, vector queries |
| Azure Data Explorer (ADX) | Big-data analytics, time-series, logs | Telemetry, log analytics, IoT analytics | KQL (Kusto Query Language) |

# 1. Azure Managed Redis

## What it is

Azure Managed Redis is Microsoft's fully managed, in-memory data store built on Redis Enterprise. It is the newer offering that succeeds Azure Cache for Redis. Data lives in memory, so reads and writes take sub-millisecond time. It supports strings, hashes, lists, sets, sorted sets, streams, and (with modules) JSON, search, time series, and Bloom filters.

SKU families: **Memory Optimized**, **Balanced**, **Compute Optimized**, and **Flash Optimized** (RAM + NVMe for larger datasets at lower cost).

## Use cases

- **Caching**: cache database query results or API responses to cut latency and load.
- **Session store**: store web session data shared across app instances.
- **Leaderboards**: sorted sets give ranked scores in real time.
- **Rate limiting**: atomic counters with expiry (TTL).
- **Pub/Sub and streams**: lightweight messaging between services.
- **Semantic cache / vector store**: cache LLM responses using vector similarity.

## Create

```bash
az redisenterprise create \
  --cluster-name my-amr-cache \
  --resource-group $RG \
  --location $LOCATION \
  --sku Balanced_B0 \
  --client-protocol Encrypted \
  --clustering-policy OSSCluster \
  --eviction-policy VolatileLRU
```

Get the endpoint and access key (default database port is `10000`):

```bash
# Hostname
az redisenterprise show --cluster-name my-amr-cache --resource-group $RG \
  --query hostName -o tsv

# Access keys
az redisenterprise database list-keys \
  --cluster-name my-amr-cache --resource-group $RG
```

> The hostname looks like `my-amr-cache.<region>.redis.azure.net`. Microsoft Entra ID authentication is also supported and preferred for production.

## Access and insert data (Python)

```python
import redis

r = redis.Redis(
    host="my-amr-cache.eastus.redis.azure.net",
    port=10000,
    password="<access-key>",
    ssl=True,
    decode_responses=True,
)

# String with expiry (cache pattern)
r.set("product:1001", '{"name":"Laptop","price":899}', ex=300)
print(r.get("product:1001"))

# Hash (object)
r.hset("user:42", mapping={"name": "Ram", "role": "teacher", "city": "Hyderabad"})
print(r.hgetall("user:42"))

# Sorted set (leaderboard)
r.zadd("leaderboard", {"alice": 120, "bob": 95, "carol": 150})
print(r.zrevrange("leaderboard", 0, 2, withscores=True))

# Counter (rate limiting)
r.incr("api:calls:user42")
r.expire("api:calls:user42", 60)

# List (queue)
r.lpush("jobs", "job1", "job2")
print(r.rpop("jobs"))
```

Using `redis-cli`:

```bash
redis-cli -h my-amr-cache.eastus.redis.azure.net -p 10000 --tls -a "<access-key>"

SET greeting "hello"
GET greeting
HSET user:1 name "Ram" role "teacher"
HGETALL user:1
```

# 2. Azure Cosmos DB

## What it is

Azure Cosmos DB is a fully managed, globally distributed NoSQL database with single-digit millisecond latency, automatic indexing, elastic scale, and multi-region writes. It offers several APIs: **NoSQL** (native, JSON documents with SQL-like queries), **MongoDB**, **Cassandra**, **Gremlin** (graph), and **Table**.

Key concepts:

- **Account → Database → Container → Items**
- **Partition key**: decides how data is distributed; choose a value with high cardinality and even access.
- **Request Units (RU/s)**: the throughput currency. Choose provisioned, autoscale, or serverless.
- **Consistency levels**: Strong, Bounded Staleness, Session (default), Consistent Prefix, Eventual.

## Use cases

- E-commerce catalogs and shopping carts
- User profiles and personalization
- IoT and telemetry ingestion
- Gaming state and leaderboards
- Globally distributed apps needing low latency everywhere
- Backing store for AI apps (vector search is supported)

## Create

```bash
# Account (NoSQL API)
az cosmosdb create \
  --name my-cosmos-demo-123 \
  --resource-group $RG \
  --locations regionName=$LOCATION failoverPriority=0 isZoneRedundant=False \
  --default-consistency-level Session

# Database
az cosmosdb sql database create \
  --account-name my-cosmos-demo-123 \
  --resource-group $RG \
  --name storedb

# Container with partition key
az cosmosdb sql container create \
  --account-name my-cosmos-demo-123 \
  --resource-group $RG \
  --database-name storedb \
  --name products \
  --partition-key-path "/category" \
  --throughput 400
```

Get the endpoint and key:

```bash
az cosmosdb show --name my-cosmos-demo-123 --resource-group $RG \
  --query documentEndpoint -o tsv

az cosmosdb keys list --name my-cosmos-demo-123 --resource-group $RG \
  --query primaryMasterKey -o tsv
```

## Access and insert data (Python)

```python
from azure.cosmos import CosmosClient

client = CosmosClient(
    url="https://my-cosmos-demo-123.documents.azure.com:443/",
    credential="<primary-key>",
)
container = client.get_database_client("storedb").get_container_client("products")

# Insert (id is required; partition key value must be in the item)
container.create_item({
    "id": "1001",
    "category": "laptops",
    "name": "ProBook 14",
    "price": 899,
    "tags": ["work", "portable"],
})

container.upsert_item({
    "id": "1002",
    "category": "laptops",
    "name": "GameBook 16",
    "price": 1499,
})

# Point read (cheapest: needs id + partition key)
item = container.read_item(item="1001", partition_key="laptops")
print(item)

# Query
results = container.query_items(
    query="SELECT c.name, c.price FROM c WHERE c.category = @cat AND c.price < @max",
    parameters=[
        {"name": "@cat", "value": "laptops"},
        {"name": "@max", "value": 1000},
    ],
    enable_cross_partition_query=False,
)
for r in results:
    print(r)
```

Sample document and SQL queries (Data Explorer in the Azure portal):

```json
{
  "id": "1001",
  "category": "laptops",
  "name": "ProBook 14",
  "price": 899
}
```

```sql
SELECT * FROM c WHERE c.category = "laptops"
SELECT VALUE COUNT(1) FROM c
SELECT c.category, AVG(c.price) AS avgPrice FROM c GROUP BY c.category
```

# 3. Azure Table Storage

## What it is

Azure Table Storage is a low-cost NoSQL key-attribute store inside an Azure Storage account. Data is stored as **entities** (rows) in **tables**, with no fixed schema. Each entity has a **PartitionKey** and **RowKey** that together form the unique primary key. It is very cheap and scales to terabytes, but it only supports querying efficiently by PartitionKey and RowKey (no secondary indexes, no joins).

> For global distribution, higher throughput, and secondary indexes, use Cosmos DB for Table (same API surface, premium features).

## Use cases

- Storing application logs and audit trails cheaply
- Device registry or user metadata
- Address books and lightweight lookup data
- Simple structured data where cost matters more than query flexibility

## Create

```bash
# Storage account
az storage account create \
  --name mystoragetable123 \
  --resource-group $RG \
  --location $LOCATION \
  --sku Standard_LRS

# Table (Entra ID auth; requires "Storage Table Data Contributor" role)
az storage table create \
  --name Employees \
  --account-name mystoragetable123 \
  --auth-mode login
```

Connection string:

```bash
az storage account show-connection-string \
  --name mystoragetable123 --resource-group $RG -o tsv
```

## Access and insert data (Python)

```python
from azure.data.tables import TableServiceClient

conn_str = "<connection-string>"
service = TableServiceClient.from_connection_string(conn_str)
table = service.get_table_client("Employees")

# Insert (PartitionKey + RowKey are mandatory)
table.create_entity({
    "PartitionKey": "Engineering",
    "RowKey": "emp001",
    "Name": "Asha",
    "Role": "DevOps Engineer",
    "Salary": 90000,
})

table.upsert_entity({
    "PartitionKey": "Engineering",
    "RowKey": "emp002",
    "Name": "Ravi",
    "Role": "SRE",
})

# Point lookup (fastest)
e = table.get_entity(partition_key="Engineering", row_key="emp001")
print(e)

# Query with filter
for ent in table.query_entities("PartitionKey eq 'Engineering' and Role eq 'SRE'"):
    print(ent)
```

Using the CLI:

```bash
az storage entity insert \
  --table-name Employees --account-name mystoragetable123 --auth-mode login \
  --entity PartitionKey=Engineering RowKey=emp003 Name=Meena Role=QA

az storage entity query \
  --table-name Employees --account-name mystoragetable123 --auth-mode login \
  --filter "PartitionKey eq 'Engineering'"
```

# 4. Azure AI Search

## What it is

Azure AI Search (formerly Azure Cognitive Search) is a managed search service that supports **full-text**, **vector**, and **hybrid** search, plus semantic ranking. It builds an **index** from your data (via push API or **indexers** that pull from Blob Storage, SQL, Cosmos DB, etc.) and can enrich content with AI skills (OCR, entity extraction, chunking, embeddings).

Key concepts: **Search service → Index → Documents**, **fields** (searchable, filterable, sortable, facetable), **indexers**, **skillsets**, **vector fields**.

## Use cases

- Search box for websites, e-commerce, and internal portals
- **RAG (Retrieval-Augmented Generation)**: retrieve relevant chunks to ground LLM answers
- Document and PDF search with OCR
- Faceted navigation and filtering
- Semantic and vector similarity search

## Create

```bash
az search service create \
  --name my-search-demo-123 \
  --resource-group $RG \
  --sku basic \
  --partition-count 1 \
  --replica-count 1 \
  --location $LOCATION

# Admin key and query key
az search admin-key show --service-name my-search-demo-123 --resource-group $RG
az search query-key list --service-name my-search-demo-123 --resource-group $RG
```

Endpoint: `https://my-search-demo-123.search.windows.net`

## Create an index, insert documents, and search (Python)

```python
from azure.core.credentials import AzureKeyCredential
from azure.search.documents import SearchClient
from azure.search.documents.indexes import SearchIndexClient
from azure.search.documents.indexes.models import (
    SearchIndex, SimpleField, SearchableField, SearchFieldDataType
)

endpoint = "https://my-search-demo-123.search.windows.net"
cred = AzureKeyCredential("<admin-key>")

# 1) Create index
index_client = SearchIndexClient(endpoint, cred)
index = SearchIndex(
    name="hotels",
    fields=[
        SimpleField(name="id", type=SearchFieldDataType.String, key=True),
        SearchableField(name="name", type=SearchFieldDataType.String, sortable=True),
        SearchableField(name="description", type=SearchFieldDataType.String),
        SimpleField(name="city", type=SearchFieldDataType.String, filterable=True, facetable=True),
        SimpleField(name="rating", type=SearchFieldDataType.Double, filterable=True, sortable=True),
    ],
)
index_client.create_or_update_index(index)

# 2) Insert (upload) documents
search_client = SearchClient(endpoint, "hotels", cred)
search_client.upload_documents(documents=[
    {"id": "1", "name": "Lakeview Inn", "description": "Quiet hotel near the lake with free breakfast", "city": "Hyderabad", "rating": 4.5},
    {"id": "2", "name": "City Central", "description": "Modern business hotel in the city center", "city": "Mumbai", "rating": 4.1},
    {"id": "3", "name": "Beach Resort", "description": "Seaside resort with pool and spa", "city": "Goa", "rating": 4.7},
])

# 3) Search
results = search_client.search(
    search_text="lake breakfast",
    filter="rating ge 4",
    select=["id", "name", "city", "rating"],
    top=5,
)
for r in results:
    print(r["name"], r["city"], r["@search.score"])
```

REST example (insert documents):

```bash
curl -X POST "https://my-search-demo-123.search.windows.net/indexes/hotels/docs/index?api-version=2024-07-01" \
  -H "Content-Type: application/json" \
  -H "api-key: <admin-key>" \
  -d '{
    "value": [
      {"@search.action": "upload", "id": "4", "name": "Hill Lodge", "description": "Mountain lodge with trekking", "city": "Manali", "rating": 4.3}
    ]
  }'
```

> For RAG, add a `Collection(Edm.Single)` vector field with a vector search profile, generate embeddings (for example with Azure OpenAI), and run vector or hybrid queries.

# 5. Azure Data Explorer (ADX)

## What it is

Azure Data Explorer is a fast, fully managed analytics service for large volumes of **log, telemetry, and time-series** data. It stores data in a columnar format, ingests streaming or batch data, and is queried with **KQL (Kusto Query Language)**. It powers services such as Azure Monitor Log Analytics and Microsoft Sentinel under the hood.

Key concepts: **Cluster → Database → Table**, **ingestion** (batch, streaming, from Event Hubs, IoT Hub, Blob/Event Grid), **retention and caching policies**, **materialized views**.

## Use cases

- Application and infrastructure log analytics
- IoT telemetry and time-series analysis
- Security analytics and threat hunting
- Near real-time dashboards (Grafana, Power BI, ADX dashboards)
- Anomaly detection and forecasting on time series

## Create

Quickest way to try it: the **free cluster** at <https://dataexplorer.azure.com/freecluster>.

Using the CLI (requires the `kusto` extension):

```bash
az extension add --name kusto

az kusto cluster create \
  --cluster-name myadxdemo123 \
  --resource-group $RG \
  --location $LOCATION \
  --sku name="Dev(No SLA)_Standard_E2a_v4" tier="Basic" capacity=1

az kusto database create \
  --cluster-name myadxdemo123 \
  --resource-group $RG \
  --database-name telemetrydb \
  --read-write-database soft-delete-period=P365D hot-cache-period=P31D location=$LOCATION
```

Cluster URI: `https://myadxdemo123.<region>.kusto.windows.net`

## Create table, insert data, and query (KQL)

Run these in the Azure Data Explorer web UI (<https://dataexplorer.azure.com>) against your database:

```kusto
// Create table
.create table DeviceTelemetry (Timestamp: datetime, DeviceId: string, Temperature: real, Humidity: real)

// Insert sample rows (inline ingestion, for testing only)
.ingest inline into table DeviceTelemetry <|
2026-01-01T10:00:00Z,dev-01,24.5,60
2026-01-01T10:05:00Z,dev-01,25.1,58
2026-01-01T10:00:00Z,dev-02,30.2,45
2026-01-01T10:05:00Z,dev-02,31.0,44

// Query: latest 10 rows
DeviceTelemetry
| take 10

// Query: average temperature per device
DeviceTelemetry
| summarize AvgTemp = avg(Temperature) by DeviceId

// Query: time-series, 5-minute bins
DeviceTelemetry
| where Timestamp > ago(30d)
| summarize AvgTemp = avg(Temperature) by bin(Timestamp, 5m), DeviceId
| render timechart
```

## Access and ingest from Python

```python
from azure.kusto.data import KustoClient, KustoConnectionStringBuilder
from azure.kusto.data.helpers import dataframe_from_result_table

cluster = "https://myadxdemo123.eastus.kusto.windows.net"
kcsb = KustoConnectionStringBuilder.with_az_cli_authentication(cluster)
client = KustoClient(kcsb)

# Query
response = client.execute("telemetrydb", """
DeviceTelemetry
| summarize AvgTemp = avg(Temperature) by DeviceId
""")
df = dataframe_from_result_table(response.primary_results[0])
print(df)

# Small insert via control command (for testing)
client.execute_mgmt("telemetrydb", """
.ingest inline into table DeviceTelemetry <|
2026-01-01T10:10:00Z,dev-01,25.8,57
""")
```

For production ingestion use the queued ingestion client (`azure-kusto-ingest`), Event Hubs / IoT Hub data connections, or Event Grid with Blob Storage.

# Choosing the Right Service

| If you need... | Choose |
|---|---|
| Sub-millisecond caching, sessions, counters | **Azure Managed Redis** |
| Globally distributed operational database with rich queries | **Cosmos DB** |
| Very cheap, simple key/attribute storage at large scale | **Table Storage** |
| Full-text, semantic, or vector search / RAG | **Azure AI Search** |
| Analytics over huge log or time-series data | **Azure Data Explorer** |

Typical combined architecture: **Cosmos DB** as the system of record, **Redis** in front as a cache, **AI Search** indexing Cosmos DB data for search, and **Data Explorer** receiving telemetry and logs for analytics.
