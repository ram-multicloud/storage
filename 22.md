# Azure File Share (NFS) — Create & Mount on Linux

A complete guide covering storage account/share creation, networking and ports, identity/permissions model, and step-by-step mounting on a Linux VM.

---

## 1. Prerequisites & Key Facts

| Requirement | Detail |
|---|---|
| Storage account kind | **FileStorage** (Premium performance tier) — NFS is **not** available on Standard (HDD-backed) file shares |
| Protocol | NFS 4.1 |
| Port | **TCP 2049** (only port needed for NFS traffic) |
| Network access | NFS shares can **only** be accessed over a **trusted network** — a Private Endpoint (recommended) or a Service Endpoint restricting the public endpoint. No public/anonymous internet access is supported. |
| Secure transfer | Must be **disabled** at the storage account level (NFS doesn't support in-transit encryption via the "Secure transfer required" setting — security instead comes from the trusted network boundary) |
| Identity model | **No Active Directory / Kerberos / username-password auth** (unlike SMB). Access control is purely **network-level** + **Linux-style UID/GID (POSIX) permissions** on files/folders |
| Client OS | Linux only (Windows/macOS cannot mount Azure NFS shares) |

## 2. Create the Storage Account & NFS Share

### Via Azure Portal
1. **Create a Storage Account**
   - Performance: **Premium**
   - Premium account type: **File shares (FileStorage)**
   - Redundancy: **LRS** or **ZRS** (NFS shares don't support GRS/GZRS)
2. Under **Networking**, set **Public network access** to *Disabled* or *Enabled from selected virtual networks and IP addresses*, and add your VM's **VNet/subnet** with the **Microsoft.Storage** service endpoint enabled (or create a **Private Endpoint** instead — recommended for production).
3. Under **Configuration**, set **Secure transfer required = Disabled**.
4. Go to **File shares → + File share**
   - Name your share
   - Protocol: **NFS**
   - Set a quota (GiB)
   - Configure **Root squash**: `No root squash` / `Root squash` / `All squash` (see Section 4)
5. Create the share.

### Via Azure CLI
```bash
# Variables
RG="myResourceGroup"
LOCATION="eastus"
SA="mynfsstorageacct"
SHARE="myshare"
VNET="myVNet"
SUBNET="mySubnet"

# 1. Create resource group (if needed)
az group create --name $RG --location $LOCATION

# 2. Create Premium FileStorage account
az storage account create \
  --name $SA \
  --resource-group $RG \
  --location $LOCATION \
  --sku Premium_LRS \
  --kind FileStorage \
  --https-only false \
  --enable-large-file-share

# 3. Restrict network access to your VNet/subnet (service endpoint)
az network vnet subnet update \
  --resource-group $RG \
  --vnet-name $VNET \
  --name $SUBNET \
  --service-endpoints Microsoft.Storage

az storage account network-rule add \
  --resource-group $RG \
  --account-name $SA \
  --vnet-name $VNET \
  --subnet $SUBNET

az storage account update \
  --name $SA \
  --resource-group $RG \
  --default-action Deny

# 4. Create the NFS file share
az storage share-rm create \
  --resource-group $RG \
  --storage-account $SA \
  --name $SHARE \
  --enabled-protocols NFS \
  --quota 1024 \
  --root-squash NoRootSquash
```

> **Private Endpoint alternative** (recommended over service endpoints):
> ```bash
> az network private-endpoint create \
>   --resource-group $RG \
>   --name pe-$SA \
>   --vnet-name $VNET \
>   --subnet $SUBNET \
>   --private-connection-resource-id $(az storage account show -n $SA -g $RG --query id -o tsv) \
>   --group-id file \
>   --connection-name pe-conn-$SA
> ```

## 3. Networking & Ports

| Port | Protocol | Purpose |
|---|---|---|
| **2049** | TCP | NFS data/control traffic — the **only** port required |
| 443 | TCP | Only relevant if you also use the Azure Portal/CLI/REST management plane against the account, not for the NFS mount itself |

**Rules:**
- The Linux client and the storage account must be able to reach each other over **port 2049** — same VNet, peered VNet, VPN (P2S/S2S), or ExpressRoute, plus a private endpoint or service endpoint.
- No NSG should block outbound/inbound TCP 2049 between the client subnet and the storage service (or private endpoint IP).
- Test connectivity before mounting:
  ```bash
  nslookup mynfsstorageacct.file.core.windows.net
  nc -zv mynfsstorageacct.file.core.windows.net 2049
  ```

## 4. Identity & Permissions Model

Azure Files **NFS** uses a fundamentally different auth model than SMB:

- **No Azure AD / AD DS / Kerberos identity is used.** There's no per-user login to the share.
- **Access control = two layers:**
  1. **Network-level:** only clients inside the allowed VNet/subnet (or via private endpoint) can even reach the share (enforced via NSG + storage firewall/private endpoint).
  2. **POSIX-style file/folder permissions:** once mounted, standard Linux `chmod`/`chown` and UID/GID rules apply, exactly like a normal Linux NFS export.
- **Root squash options** (set at share creation or later):
  | Option | Behavior |
  |---|---|
  | **No Root Squash** | Root on the client keeps root (UID 0) privileges on the share — full read/write/delete anywhere |
  | **Root Squash** | Root's UID/GID is mapped to the anonymous user (`nobody`/`nogroup`), restricting root's access like a normal user |
  | **All Squash** | *Every* client user, including non-root, is mapped to the anonymous user |
- Set/inspect permissions after mounting using normal Linux tools:
  ```bash
  # Change owner/group
  sudo chown myuser:mygroup /mnt/nfsshare/somefile
  # Change mode
  sudo chmod 750 /mnt/nfsshare/somefile
  ```
- Because there's no identity federation, **UID/GID values must be consistent across all clients** that mount the share if you want consistent ownership/permissions semantics (similar to any classic NFS setup).

## 5. Step-by-Step: Mount on a Linux VM

### Step 1 — Install the NFS client package
```bash
# Ubuntu/Debian
sudo apt-get update && sudo apt-get install -y nfs-common

# RHEL/CentOS/Rocky/Alma
sudo yum install -y nfs-utils
```

### Step 2 — Create a local mount point
```bash
sudo mkdir -p /mnt/nfsshare
```

### Step 3 — Verify connectivity
```bash
nslookup mynfsstorageacct.file.core.windows.net
nc -zv mynfsstorageacct.file.core.windows.net 2049
```

### Step 4 — Mount the share
```bash
sudo mount -t nfs \
  mynfsstorageacct.file.core.windows.net:/mynfsstorageacct/myshare \
  /mnt/nfsshare \
  -o vers=4,minorversion=1,sec=sys
```

### Step 5 — Verify the mount
```bash
mount | grep nfsshare
df -h /mnt/nfsshare
```

### Step 6 — Persist across reboots (`/etc/fstab`)
```bash
echo "mynfsstorageacct.file.core.windows.net:/mynfsstorageacct/myshare /mnt/nfsshare nfs vers=4,minorversion=1,sec=sys 0 0" | sudo tee -a /etc/fstab

# Test the fstab entry without rebooting
sudo umount /mnt/nfsshare
sudo mount -a
```

### Step 7 — Test read/write access
```bash
id                                  # check your current UID/GID
touch /mnt/nfsshare/testfile.txt
ls -la /mnt/nfsshare/
echo "hello" > /mnt/nfsshare/testfile.txt
cat /mnt/nfsshare/testfile.txt
```

## 6. Recommended Mount Options

| Option | Purpose |
|---|---|
| `vers=4,minorversion=1` | Forces NFS 4.1 (required by Azure Files NFS) |
| `sec=sys` | Standard UNIX (AUTH_SYS) security, the only supported mode |
| `rsize=1048576,wsize=1048576` | Max I/O read/write size for better throughput |
| `hard,timeo=600,retrans=2` | Hard mount with generous timeout — recommended for resilience over WAN/VPN links |
| `noresvport` | Client uses a non-reserved source port; improves reconnection behavior |

Example tuned mount:
```bash
sudo mount -t nfs \
  mynfsstorageacct.file.core.windows.net:/mynfsstorageacct/myshare \
  /mnt/nfsshare \
  -o rw,hard,timeo=600,retrans=2,vers=4.1,rsize=1048576,wsize=1048576,sec=sys,noresvport
```

## 7. Troubleshooting Quick Reference

| Symptom | Likely Cause | Fix |
|---|---|---|
| `mount.nfs: Connection timed out` | Port 2049 blocked, or client not on an allowed network | Check NSG rules, storage account network rules, private endpoint DNS resolution |
| `Permission denied` on file ops | Root squash mapping, or UID/GID mismatch | Check `id`, adjust root-squash setting or file ownership |
| `Stale file handle` | Storage account/network blip or share was modified | `sudo umount -f /mnt/nfsshare && sudo mount -a` |
| DNS resolves to a public IP unexpectedly | Private endpoint/service endpoint misconfigured | Recheck private DNS zone linkage or VNet service endpoint |
| Mount hangs indefinitely | `hard` mount + unreachable server | Verify connectivity with `nc -zv <account>.file.core.windows.net 2049` first |

---

### Summary
1. Create a **Premium FileStorage** account with an **NFS** file share.
2. Lock network access down via **VNet service endpoint or private endpoint** — disable secure transfer.
3. Open/allow **TCP 2049** between client and storage.
4. Permissions are enforced via **network trust + POSIX UID/GID + root squash**, not Azure AD identities.
5. Install `nfs-common`/`nfs-utils`, mount with `vers=4.1,sec=sys`, and persist via `/etc/fstab`.
